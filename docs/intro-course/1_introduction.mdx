# 1. A Brief Introduction

## The End Goal of Embedded Programming

In embedded programming, the end goal is always to fetch an input (sense),
manipulate it, and produce some output (actuate). The input may be a sensor
reading, an interrupt, a switch, or even a timer, and the output will be an
action performed, be it moving a motor, blinking an LED, playing a sound or
sending a message. The same is true on a satellite. Our sensors range from
environmental and inertial measurement to command reception and mission status.
The actuators include ADCS and heating, as well as beacons and comms. The end
goal will always be to produce the correct actuation, based on a given sense.

## What's an RTOS?

An RTOS, or *real time operating system*, is an underlying program facilitating
for the execution of concurrent tasks. Whereas a simple program may perform its
instructions one by one, an operating system splits it's resources,
interweaving the instructions to allow for the impression of doing several
tasks at once. The *real time* modifier signifies another level of fine-grained
control of this *scheduling*, allowing for precise timers, recurring tasks,
priority-based execution. This means we can set a task to be executed once
every *n* seconds/milliseconds and the RTOS will manage it for us.

## Complicating a Simple Task - Why Zephyr?

Zephyr is an RTOS offering not only the aforementioned scheduling, but also a
solution to a prominent issue in embedded programming. When developing
applications you're stuck developing both the manipulating application as well
as the interface for the hardware. Varying hardware capabilities affect how you
write your application, and the intermingling of these makes modifications and
replacements an often arduous process. The goal of the Zephyr model is to solve
this.

Zephyr RTOS organizes an embedded project into three parts: the API, the
application, and the implementation. The API is a generic hardware description
providing functions typically expected of a category of hardware (e.g. a sensor
API might expose functionality for sensor reading or configuration while a
clock API might let you set/get the time as well as toggling between 12/24-hour
mode). This implements no functionality, but simply describes what can be
expected of a category of hardware. The application is where all the logic
happens.

The application utilizes the functions provided by the API to fetch data,
actuate its outputs manage the scheduler and all else a typical application
would do. It doesn't care for how the sensors works, it's completely
uninterested in the specifics of an actuator; all that matters is that it's
described by the API, and the application will assume it exists.

All the details of the hardware, how it's connected, what registers it
features, what bus to use, are described in the implementation. This is where
we make good on our promise that everything we describe in the API is actually
possible. If our API promises a function to read a temperature, this is where
we implement the function for our specific hardware. Our sensor might be
connected to the I²C-bus with a configuration register requiring some
manipulation in order to be properly initialized - this is all encapsulated in
the implementation, the application shouldn't need to know. Our implementation
handles the I²C communication and everything specific to the sensor, and
connects a read function with all the nitty-gritty details to the pretty
function from the temperature API. Perhaps we're using several different
sensors? Well, the application shouldn't have to care - all that matters is
getting the temperature. These different sensors will all be encapsulated in
their own separate implementations, implementing the same API.

You might wonder how this all works? Aside from a heavy dose of macro-magic,
it's mostly made possible by the devicetree. We'll get back to this, after a
brief discussion of the project structure and build system.
